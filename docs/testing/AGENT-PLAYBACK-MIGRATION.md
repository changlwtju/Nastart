# Agent 接入与播放迁移边界

2026-10-07：回应用户担心后续改用 Agent 连接 Docker 服务会使已有播放优化失效。本文记录当前实现及未来迁移验收，不代表已部署 Agent 或已验证 Agent 视频转发。

## 当前代码结论

- `agent/nastart_agent.py` 只提供配对、健康检查、握手、状态快照与诊断；没有媒体流、Range 或 HLS 转发接口。
- `DSMNASDataSource.loadSnapshot()` 先读取 DSM，再用 Agent 补容器/主机信息。Agent 查询失败保留 DSM 数据；该快照容错不代表所有未实现的 Agent 功能都具备播放容错。
- `AgentSnapshotMerger` 保留 DSM 文件/媒体列表、已有服务 ID 和已有 endpoint，仅补缺失 endpoint 或新增服务。新服务地址由 Agent 访问地址的主机和容器公开端口组合，因此仍须验证 LAN/公网/蜂窝可达性，不能将 Docker 内部地址直接当手机可用地址。
- 文件访问继续使用 DSM/File Station 会话；Jellyfin 用户会话与 Agent 配对令牌各自独立。发现容器不等于获得该服务的媒体访问权限。
- 播放层已有 `MediaPlaybackRequest` / `MediaPlaybackResource` 与 `PlaybackRoute`，包含媒体 URL、原始来源、轨道、时间轴、Range 能力和编码信息。未来接入层应生成这些现有结构并复用播放逻辑；这些边界不代表纯 Agent 文件提供方已经实现。

## 两类迁移

| 方案 | 可保留的工作 | 必须重新验证的部分 |
| --- | --- | --- |
| Agent 发现、状态查询、获取地址，App 直接向 DSM/Jellyfin 读取视频 | 已有解码、播放控制、字幕、缓冲和质量切换逻辑 | 服务身份与地址匹配、登录/过期重连、证书、LAN/公网切换、规则 VPN 路由，以及两个入口真实播放 |
| 视频也经 Agent 转发，或 Agent 成为纯文件提供方 | 播放器与界面逻辑仍可复用 | 新传输层的大偏移 Range/206、Content-Range/总长度、流式交付与内存、HLS 清单/分段/时间轴、取消/背压、超时、轨道与转码会话、实际终端供流测速 |

推荐第一阶段保持服务发现与媒体传输分开，媒体直读为现有路径；遇到直读不可达时再设计有明确能力说明的中转路径。用户本次未要求部署 Agent 或改写播放路径。

## 后续接入门槛

1. 记录实际播放路径，区分 App→媒体服务与 App→Agent→媒体服务；Agent 在线不等于媒体可达。
2. 地址变化仍匹配同一 NAS/Jellyfin 与对应会话，保留原 ID、断点及轨道偏好；Agent 离线、容器重启和令牌过期分别验证。
3. 同源码、同构建配置、逐机核对最新包，对比原连接与 Agent 连接；不能用旧包或不同 Debug/Release 作性能归因。
4. 主线覆盖 S19（128,795,641,934 bytes）及 MI2/S03，设备文件和 Jellyfin 分别测试 LAN、真实弱蜂窝、原 Shadowrocket 配置规则 VPN；不得由小片或单入口推断通过。
5. 中转场景必须验证百 GB 文件尾部大偏移跳转、连续有限 Range、HLS 分段鉴权/相对 URL、时间轴与取消释放；不能把整部文件读入内存。
6. 对照点击至真实首帧、稳态卡顿/掉帧、画质/码率、暂停跳转、恢复、字幕和音轨实际效果、退出及内存。中转的 NAS→Agent 速度不能冒充 App 的可用下载速度。
7. 同时遵循现有 PLAYBACK-DEBUG-RUNBOOK 和 COMPETITOR-DEVICE-MATRIX；失败/超时保留，缺完整显示、字幕或音频证据仍未验收。

当前视频优化尚有大文件卡顿、自动升档、内存异常与完整矩阵未完成项。Agent 接入不会自动消除这些问题，也不意味着已有优化需要从头重写。
