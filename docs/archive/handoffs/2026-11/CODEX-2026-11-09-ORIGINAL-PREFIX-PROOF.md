## 可消费的字节

`prepareOriginalStartupPrefix` 提供显式准备入口。目前 App 的播放准备未调用该入口。它在已注册、可撤销的 HTTP 原流路由上读取一个从字节 0 开始的范围。代理只留一个预读槽，每次最多 256 KiB，源端请求的资源超时为 2 秒，读到的字节保留 2 秒或到首次匹配读取。预读要求 206、精确范围及长度、强 ETag 和 identity 编码，拒绝重定向、`no-store` 及当前未处理的 `Vary`。本批仅支持常规 TLS 或 HTTP 的原流，不启用自签证书路线、网络媒体库桥接或 HLS。路由撤销时取消对应准备并丢弃字节。

同一路由收到从 0 开始的无条件、开放结束 GET 后，代理用 `If-Range` 从预读末端继续向上游请求。首个续读响应通过 ETag、范围、表示长度及 URL 核对后，预读和实时读取共用原有发送缓冲，向播放器交付一个连续 206。首次校验失败会丢弃预读，从原请求起点重新取流。已经发送响应后，后续版本不匹配则终止该响应。预读获取和代理交付分别记录 `originalPrefixPrepared` 和 `originalPrefixDelivered`，缓存字节不进入源端吞吐估计。[HTTP If-Range 语义](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.5)

## 验证结果

- 首轮 7 项通过。最终 9 项通过，包括 KSPlayer 对本机合成 H.264 视频的预读消费、原流候选预览、跨窗完整响应、版本校验失败回退、撤销、既有 Range 与桥接回归，以及默认观察型 IO 仍报 0。
- 跨窗测试的 33,554,448 字节响应逐字节相等。上游只读 `0-3`、`4-33554431` 和 `33554432-33554447` 三段，后两段携带同一 `If-Range`，首段没有重取。ETag 变更、表示总长度变化、上游改回 200 的三组反例均只向客户端交付重新读取后的内容。
- KSPlayer 用同一个代理 URL 打开并解码合成视频，完成暂停预览对齐。日志中先获取 512 字节，再向播放器发送 512 字节。上游随后从 512 开始读取并携带 `If-Range`。这是解码器使用预读的证据，未测真实屏幕首帧或速度收益。

Jellyfin、设备文件和网络存储仍按既有路径启动，默认观察型 IO 的 `bytesNotMaterialized / 0` 保留。网络媒体库现有桥接的 206 不带强 ETag，下一步应把协议 Reader 的已校验文件版本接到共享取字节边界，再统一衡量真实获取和消费。真机实验前先核真实 HTTP 来源有无可用版本标识，并选择能与既有准备重叠的读取时机。避免在首帧关键路径串行增加一个源端请求。待验证相同媒体及落点下的正常起播、续播和跳转，保留缓存不命中、取消和真实首帧证据。
