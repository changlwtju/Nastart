## 变更卡

- 基线：`b4c789a` + `work/nas-20260914` 已有未提交的首批生命周期修复及流程文档。此次修改也保留本地，Swift 尚未编译。
- 反例一：账号 A 准备 tracker → 事件 Task 尚未执行 → 替换为账号 B 的 client → 旧 `reportPlayback` 读取 store 当前 client。源码允许旧事件使用 B 的凭据上报 A 的媒体。
- 反例二：A 的 stopped 请求已发送 → 退出/更换账号 → 请求返回 → 原代码调用当前 store 的 resume loader 并写入当前 UI；旧操作继续影响新会话。
- 反例三：同账号首页 resume 请求 R1 → 停止后刷新 R2 → R2 返回后 R1 才返回 → 原先两处直接赋值允许 R1 覆盖新列表。
- 成功条件：旧认证会话事件不能使用替换后的 client；已发送旧请求的结果不能继续刷新新会话；resume 只接受当前会话最新发起的请求，并在同一次 MainActor 执行中校验、映射和写入。
- 非退化条件：正常账号仍可开始/进度/停止上报；资源清理继续使用准备时的 client/session；失败保留已有列表，可由新请求重试；不改双入口绝对时间、轨道或清晰度接口。

## 实现与证据范围

`LaunchpadPlaybackCore.swift` 新增 `PlaybackResponseScope`：认证会话 UUID、resume 请求 UUID 及有效性判断，不保存账号、凭据或媒体数据。客户端替换/清空就使所有旧 token 失效，重新登录同账号也视为新会话。

`LaunchpadView.swift` 中：

1. `makePlaybackTracker` 捕获准备时 client 和认证会话 ID；`reportPlayback` 在开始处理时验证身份，停止请求返回后再次验证，再允许刷新。旧会话错误也不写进新会话的上报失败日志。
2. `refreshResumeItems(sessionID:)` 合并原两处“获取再赋值”的路径。进入时核对调用者会话；返回时检查取消、会话和最新请求 ID，然后原子地发布继续观看列表及收藏状态。不能把已检查的数组返回给一个可能继续挂起的调用者后再无条件赋值。
3. 首页各 shelf 的 await 后、错误写入前核对会话，避免退出后旧列表重新填回；详情响应在映射/注册收藏/发起预探测前同样检查会话。
4. 替换 client 清除 store 停止快照；首批详情页收到 nil 后清除本页快照。未改变资源释放闭包的清理身份。

新增 4 项 XCTest：重新登录不复活旧 tracker 身份；R2/R1 逆序完成；退出后即使尚无新请求也拒绝旧响应；新请求失败不使旧响应重新有效、重试可继续。与首批 4 项共 8 项新增测试，均待 Mac 执行。这些测试覆盖 scope 规则，SDK 网络集成和 SwiftUI 更新另需以下真机/受控响应验证。

## 尚未解决的边界与下一步

- **不是 JSON 解码 SIGBUS 的根因结论。** 仍需 Mac 核对 ASan 安装包/进程并捕获崩溃。
- start/progress/stop 仍各自创建网络 Task；同一认证会话内的请求完成顺序、快速更换播放会话的旧事件仍未串行化。认证会话 token 不是播放会话序列号。下一批针对这条链路设计有界队列、最新进度合并、失败推进及重复 stop 的确定性测试，再决定实现。
- resume 的“最新”定义为请求发起顺序，不能保证服务器响应包含最新观看状态；旧 stopped 在服务端晚处理仍需要上报顺序工作解决。
- 已发往旧账号的 HTTP 请求未强制撤回；本批阻止它切换身份或写入新会话，不承诺服务器取消。
- 认证 signIn/restore 本身的并发竞争、所有搜索/其他详情子请求的全覆盖隔离不在本批范围；不能将此次结果推广为全应用账号隔离已验收。
- 新 resume 请求失败时保留当前显示数据，旧请求也不会重新取得写入资格；需要一次明确重试才能更新。
