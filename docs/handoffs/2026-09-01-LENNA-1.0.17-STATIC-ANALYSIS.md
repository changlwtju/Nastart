## 当前播放链路判断

静态证据支持的 Lenna 架构模型如下：

```text
多来源媒体入口
  ├─ 本地文件 / URL / AirDrop / Document Browser
  ├─ SMB / WebDAV / 局域网发现
  ├─ Emby / Jellyfin / Plex
  └─ 阿里云盘 / 百度网盘 / 115 / 123pan / Dropbox / Drive / OneDrive / pCloud / Box

播放业务层
  ├─ PlaybackInfo / MediaSource / MediaStream 预取与排序
  ├─ requiredHttpHeaders / directStreamUrl / transcodingUrl / videoRange / cachePath
  ├─ 下一集 PlaybackInfo 与 200MB 预加载
  ├─ 音轨 / 字幕 / 弹幕 / 片段跳过 / 进度同步
  └─ LnKSOptions / FileServerKSOptions 统一配置

播放内核层
  ├─ KSPlayerLayer
  │   ├─ KSAVPlayer：AVPlayer / AVAsset 路径
  │   └─ KSMEPlayer：FFmpeg + VideoToolbox + Metal 路径
  ├─ PreLoadIOContext / CacheIOContext / ReadCacheIOContext
  │   └─ Range 判断、磁盘缓存、逻辑位置映射、seek/read 包装
  └─ ProAVPlayer
      └─ DemuxerIO / RemuxerIOAction / LocalHLSServer / HLS fMP4
```

这仍是静态模型，不等于某个具体视频实际走哪条路径。需要动态采集来确认不同来源、不同格式、不同设置下的真实分支。

## 与 DS One 静态结论的关键对比

共同点：

1. 都使用 KSPlayer，并包含 AVPlayer 路径与 FFmpeg/VideoToolbox/Metal 路径。
2. 都出现 `PreLoadIOContext`、`CacheIOContext`、`ReadCacheIOContext`、`LimitPreLoadIOContext`、`LimitCountPreLoadIOContext`、`LimitSeparatePreLoadIOContext`。
3. 都命中 `isRangeUncached(start:end:)`、`ffurl_seek2`、`performSeek(time:flags:)`、`use packet cache seek` 等缓存/seek 强证据。
4. 都围绕 Emby/Jellyfin 的 `PlaybackInfo`、`MediaSourceInfo`、`MediaStream`、`RequiredHttpHeaders`、`DirectStreamUrl`、`VideoRange`、`CachePath` 做播放准备。
5. 都将字幕、音轨、硬解、转码、下一集/连续播放纳入播放器业务层。

Lenna 更突出的点：

1. 播放设置暴露更完整：`playerType`、`videoDecodeType`、`hardwareDecode`、`enableMetal`、`isAccurateSeek`、`persistentConnection`、PiP 自动启动、后台播放、播放日志、MetalFX 超分等都在静态字符串中直接可见。
2. 有 `ProAVPlayer` / `LocalHLSServer` / `ConversionToM3U8` 路径，疑似为兼容性提供本地 HLS/remux 方案。
3. 多来源覆盖更广，除 Emby/Jellyfin/Plex 外还集成 SMB、WebDAV、多家网盘、Trakt/Simkl。
4. 播放器 UI 层保留更丰富的统计 HUD、网络速度、码率、FPS、编码、分辨率、片段跳过和播放器日志导出能力。
5. 内置弹幕生态更完整，包括 DanmakuKit、外部弹幕 API、弹幕搜索/剧集匹配/调度/渲染/统计。

## 对 Nastart 的直接启示

1. 播放能力应该拆成“来源解析、播放源决策、IO/缓存、播放器内核、体验层”五层，而不是把所有逻辑塞进播放器页面。
2. 缓存/Range 是核心竞争力：需要独立的 IOContext，明确支持逻辑位置、Range 未命中判断、seek 回退、读失败清理和磁盘缓存容量控制。
3. 下一集预加载要产品化：Lenna 明确使用“下一集预取 + 200MB 磁盘预加载”概念，Nastart 可先做可观测的轻量版本。
4. 保留至少两条播放路径：AVPlayer 用于系统能力和低功耗，FFmpeg/VideoToolbox/Metal 用于复杂格式；ProAVPlayer 式本地 HLS/remux 可作为兼容性增强路线。
5. 起播前应该缓存 `PlaybackInfo`、`MediaSource`、字幕流和下一集信息，减少点击播放后的串行等待。
6. 播放调试信息要做成用户/开发者都能用的功能：FPS、码率、分辨率、解码路径、网络速度、缓存命中、播放器日志导出。
7. 字幕不是附加功能：外部字幕、本地目录匹配、在线字幕、双字幕、HDR 字幕、字幕样式都在 Lenna 中构成完整体验。
8. 对 Emby/Jellyfin/Plex 的播放策略要显式建模：DirectPlay、DirectStream、Transcode、RequiredHttpHeaders、VideoRange、CachePath、CanSeek 应该进入 Nastart 的播放决策模型。

## 建议的下一步动态验证

1. 在真机安装 Lenna 1.0.17，用同一台 Emby/Jellyfin 服务和同一部测试片源，与 Nastart/DS One 做三方对齐。
2. 采集启动播放、首帧、seek、暂停后恢复、下一集切换、字幕切换、PiP 进入/退出的时间点。
3. 使用 mitmproxy 或服务端访问日志记录 HTTP Range、DirectPlay/DirectStream/Transcode URL、请求头和响应码。
